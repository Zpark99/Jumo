- **🔴 운영 cron이 평일 4회 전부 실패했는데 5일간 아무도 몰랐다 (#165·#166)**: 10/19 확인 결과 Vercel → Environment Variables에 **`CRON_SECRET`이 없다**(Project·Shared 탭 모두). 라우트는 fail-closed라 매번 401 — Observability → Cron Jobs에 16시대 호출 **4XX**, KIS 외부 호출 0. 결과로 `price_quotes.fetched_at`은 **10-14 12:08**(PR #167 수동 호출분)에 멈췄고, `asset_snapshots`는 10/15~10/19 **5일 연속 같은 값(9,956,250)**, 랭킹도 묵은 시세로 계산 중. 코드 결함은 없지만 **"운영 설정이 됐다"는 코멘트(10/14 "등록 완료")가 대시보드를 다시 열어 확인한 결과가 아니었고**, PR #169의 "배포 후 확인 — 17시 이후 `fetched_at` 갱신" 항목이 실행되지 않았다. 지난 회고가 만든 `[운영]` 이슈 규칙은 **추적은 성공했지만 검증 없이 닫히는 구멍**이 그대로였다.
- **Hobby 플랜에서 cron 실패를 사후 추적할 수단이 거의 없다**: Logs 보관 **1시간**(12시간 이상은 Pro), Observability → Cron Jobs는 12시간 창에 4XX 카운트만. 10/14~10/16 실행은 아무 흔적도 남지 않았고 **DB의 `fetched_at`이 유일한 증거**였다. "MM/DD 기준" 표기가 설계대로 묵음을 드러내고 있었지만, 그 표기를 볼 사람(사용자)이 5일간 홈을 안 열면 의미가 없다.
- **코딩 이틀 + 공백 사흘**: 10-13(13~19시 10커밋)·10-14(10~11시 5커밋)에 PR 17건이 몰렸고, 10-15~10-17은 활동 0. 몰린 날 자체는 문제가 아니지만, **마지막 날 오전에 cron을 올리고 그날 오후 첫 실행을 아무도 안 본 채 사흘이 비었다**는 순서가 위 사고의 직접 원인이다.

- **cron·자동화는 "첫 실행 결과 확인"을 DoD에 넣는다**: 잡을 만든 PR이 아니라 **첫 스케줄 실행이 지난 뒤** 이슈를 닫는다. pg_cron은 `cron.job_run_details`, Vercel은 Observability → Cron Jobs(12시간 안에 봐야 함) + DB 날짜 컬럼. #157은 이렇게 닫혔고(10/14 아침 확인), #165는 아니었다.
- **Hobby 관측 공백을 DB로 메운다**: Vercel 로그가 1시간이면 **결과를 DB에 남기는 쪽**이 싸다. 당장은 `price_quotes.fetched_at`으로 충분하지만, 홈 목록의 "MM/DD 기준"이 **평일 기준 2일 이상** 묵으면 눈에 띄는 색(`text-danger`)으로 바꾸는 1줄을 고려한다 — 사용자가 홈만 열어도 cron 실패가 보이게.
- **CLAUDE.md에 승격 규칙 10분 (이번 회고 PR 범위 밖, 다음 작업 전 선행)**: `release:` PR 양식(포함 커밋 표·이슈·배포 후 확인 목록), 머지 = Production 자동 배포, 배포 후 확인은 **당일** 수행. 네 번 이월이면 적는 데 걸리는 시간보다 회고에 적는 시간이 더 들었다.
- **동결까지 남은 일을 날짜에 박는다**: 10/31까지 12일. 09 로드맵 마지막 항목(전 화면 모바일 회귀 · 08 체크리스트 · README · 07 명세 · 최종 회고 → `v1.0` 태그)을 **이슈 1개 + 날짜**로 만든다. 이번 주처럼 "이틀 몰아서"가 되더라도 그 이틀이 언제인지는 정해둔다.
- **자동화는 끝까지 따라가 본다**: "스냅샷 cron이 있다"와 "랭킹이 자동 갱신된다"는 다른 문장이다. 새 자동화를 만들면 **최종 사용자 화면의 값이 바뀌는 것**까지 확인하고 닫는다(#157의 교훈).
